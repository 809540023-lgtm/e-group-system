# 日本日貨代購網站完整系統規劃書

版本 1.0　規劃日期 2026 年 10 月 8 日　適用對象 網站負責人與兩至三位管理人員

本計畫建立一套可持續擴充的日本日貨代購系統，讓商品整理、採購、臺灣銷售、金流、物流、客服、廣告及員工工作都使用同一組商品與訂單紀錄。建議以 Google 雲端作為商品來源、PostgreSQL 作為交易資料庫、GitHub 作為程式及任務協作平臺、LINE 官方帳號作為客服與工作通知入口。Grok Bot 統籌工作與查核，雲端桌面的 DeepSeek 方案負責主要程式開發及大量資料整理。

交付分成營運規劃、可逐項貼給 AI 的指令，以及可執行的開發起始程式。起始程式提供介面示範、商品同步預覽、售價計算、付款驗證、交易資料表與測試；正式會員、訂單 API、真實金流、完整後臺及各平臺廣告串接，依工作指令逐項實作與驗收。正式啟用前使用測試環境與測試帳號。


## 01 建置範圍與核心決策

本版先以 GitHub 管理程式協作、Google 管理商品來源、LINE 官方帳號管理通知與客服。協作平台名稱、DeepSeek 雲端桌面服務商與實際帳號權益仍待確認；若與你的實際平台不同，保留交易架構並替換對應 adapter。以下帳號與部署步驟是執行計畫，尚未代為開通服務。


### 先把一條完整交易流程做好

第一版先讓經審核商品可以上架，消費者能選商品、看到完整費用、付款、查訂單，員工能採購、出貨及對帳。面膜、保養品、保健食品、好市多與後續日本 DM 共用商品模型；不同品類有各自的輸入、標示、效期及配送條件。廣告平臺共用素材與成效看板，分別儲存平臺設定。

### 運作設定

臺灣消費者看到繁體中文與新臺幣售價。日本採購以日圓記帳；日本來源不等於日本製造，產地單獨儲存。來源試算表若已完成臺幣加價，匯入後直接使用已核准售價，不能再套用一次加價。商品成本、銷售價格與促銷折扣各自儲存版本。

正式營運設定需填入品牌名稱、對外銷售法律主體、銀行及金流特店資料、商品來源檔案 ID、網域、物流合約、退換貨條款、廣告帳號與預算。每個環境有獨立憑證。DeepSeek API 的官方模型 ID 為 deepseek-flash，對應 V4.1 Flash；桌面使用權與 API 計費設定分開記錄。[S03]

### 共用核心與外部服務

資料流程為「DM 與圖片存入 Drive → OCR 或既有 Excel 流程整理 → 商品人員核准 → 同步預覽 → 商品草稿 → 發布版本 → 網站與廣告商品資料」。消費者流程為「商品頁 → 購物車 → 伺服器報價 → 訂單與庫存保留 → 金流確認 → 採購或出貨 → 物流回報 → 對帳與售後」。

外部服務使用 adapter 介面，避免換金流或物流時重寫訂單核心。Grok Bot 與 DeepSeek 透過任務、檔案與受控工具參與流程；網站正常營業、付款通知與排程不依賴雲端桌面持續開機。

### 同步執行順序

1. 建議每天台北時間 06:00 執行完整同步；來源完成核準時可觸發增量同步。後臺保留「立即同步」按鈕。

2. 取得來源檔案 ID、版本、完整讀取狀態與欄位 mapping。驗證 SKU、規格、價格、重量、URL 及重複列。

3. 正規化後計算逐列 source_hash 與整批 snapshot_hash。雜湊只包含業務欄位，排除本次抓取時間和欄位順序。

4. 整批有錯誤、讀取不完整或空表時保留上一次發布版本，產生錯誤報告。不要將半張表視為新的完整商品目錄。

5. 產生新增、變更、明確下架申請及未出現在本批的 SKU 清單。缺列不等於下架，更不等於刪除歷史訂單。

6. 價格變動超過建議門檻 15%、來源突然大量縮減、進口審核待辦或規格改動時送審。門檻可在後臺設定。

7. 核准後在單一資料庫交易更新指定來源欄位，形成新發布版本，再重新整理頁面快取與廣告 feed。

8. 同一批重跑保持冪等。以來源鎖防止排程與人工同步同時發布；每次同步有紀錄、差異及可回復版本。

Google API 有配額與錯誤重試規則，採批次讀取、指數退避及 jitter，避免每一列個別呼叫。[S05] 來源超過建議 48 小時未確認時，顯示更新狀態並暫停需即時供貨的結帳；已核准固定庫存價可另外設定有效期間。


## 04 商品上架與分析工作臺


### 從圖片到可賣商品

輸入支援圖片、PDF DM、Excel、網址、JAN 與品牌型號。先由程式取得檔案與版次，再由 AI 提取原文名稱、價格、數量、規格、效期與來源位置。每個提取值附原圖頁碼或區域、信心與需確認原因。低信心價格、包裝數量、OCR 負號或促銷期限，進入人工待辦。

同款比價以 JAN、品牌、型號、容量與包裝數量的組合判定。平臺價格、運費、最低採購量及查詢時間分開儲存；不同包數或疑似平行輸入版不能直接混算。大量比價使用平臺準許的 API 或授權資料，對沒有可用介面的來源先提供人工結果輸入欄。

上架草稿包括標題、圖片、規格、售價、供貨方式、到貨區間、產地、注意事項、來源與合法銷售核准。審核畫面同時顯示原圖、OCR、翻譯及網站預覽。不同品類需完成對應檢核才可發布。緊急下架可由授權人直接執行並留下原因。


### 定價與採購建議

落地變動成本包括日本購價換算、當地運費、國際運費分攤、可歸屬稅費、報關費、包裝、臺灣配送補貼、金流及預期行銷成本。可扣抵稅額、公司固定費用與不可扣抵成本的處理交由財務設定，避免重複計入。

最低售價使用「固定型變動成本 ÷ 一減比例費率減目標貢獻率」並向上取整元。例：固定型變動成本 NT$250、金流比例費率 3%、目標貢獻率 25%，最低售價為 NT$348。這是示範計算，費率與匯率由實際合約設定；25% 貢獻率不是成本加價 25%。

最高日本採購價由可用收入扣除其他成本與目標貢獻後，再除以採購匯率及必要換算係數。結果為負數或進口條件未核准時不產生採購建議。AI 評分可採毛貢獻、同款價格差、供應穩定度、配送可行性、儲存期限及歷史需求的加權分數；權重、輸入與理由都需保留。


## 05 網站選單與長者操作設計


### 前臺資訊架構

主要入口保留首頁、商品分類、購物車、訂單查詢與客服。商品分類下設面膜、保養品、保健食品、食品飲料、生活用品；好市多、日本 DM 本期選物、臺灣現貨及日本預購作為專區。品牌、來源、功效描述與商品屬性可篩選，不把首頁堆滿多層選單。

首頁顯示一句購物說明、清楚分類、近期商品、現貨或預購說明及客服入口。商品卡只顯示圖片、名稱、關鍵規格、臺幣售價、供貨方式與「加入購物車」。原價折扣只有可驗證基準價時才顯示。廣告導流使用與該廣告一致的專區頁，不讓消費者重新尋找商品。

### UI 規格與驗收

正文建議 20 px，商品名至少 22 px，價格 28 至 32 px；按鈕高度至少 48 px，數量加減有文字與可辨識符號。依 WCAG 2.2 AA 原則設計對比、鍵盤操作、焦點、標籤及錯誤提示。[S13] 字放大至 200% 後資訊仍可用，不能只以顏色表示付款狀態。

手機以單欄結帳、大按鈕、固定購物車入口及簡單進度文字為主。避免自動輪播、搶焦點彈窗、隱藏運費、短倒數及必須滑動才能看到的主要按鈕。每一步送出後有明確結果；按付款按鈕後暫時停用並顯示處理中，重試沿用同一訂單。

成品驗收安排至少三位實際長者操作「找到商品、選規格、加購、確認總額、查訂單」五個任務，記錄完成時間、卡住位置及求助次數。美觀透過一致字級、留白、真實商品圖與柔和色彩建立，不增加操作層級。


## 06 購物車與訂單交易規則


### 現貨與預購分開計算

臺灣現貨依可售庫存成交；日本預購依採購批次、可採購配額、供應確認期限及交貨承諾成交；重量、運送或進口條件待確認者使用詢價。混合購物車先分配送包裹，讓消費者選擇分批出貨或等齊合併，不承諾所有商品共用同一到貨日。

伺服器接受 SKU 和數量，重新讀取核准售價、版本、可售量與配送規則。前端傳來的價格、付款狀態、員工角色與運費不能直接相信。產生有效期 15 分鐘的報價快照；臺幣以最小單位整數儲存，日圓購價以整數儲存，匯率使用固定精度。

訂單建立、明細與庫存保留在同一交易完成。多 SKU 按固定 SKU 順序鎖定庫存，避免兩張組合訂單形成相反鎖定順序。支付重試沿用訂單或生成有關聯的新 payment_attempt；每次請求都有 idempotency key。庫存保留不是實際出貨扣庫存，成功付款時再把保留轉成已售出。


### 狀態與異常

付款、訂單及物流各有狀態。付款為未付款、處理中、已收款、部分退款、已退款或待核對；業務為待付款、已成立、待採購、已備貨、取消或異常；物流為未出貨、已出貨、清關中、臺灣配送中、已送達或配送異常。前臺顯示簡明文字，後臺儲存事件歷史。

逾期釋放庫存前先檢查金流是否可能已完成。ATM 或超商付款的有效期與庫存保留方案配套，不能用信用卡短保留時間處理數日後才可能付款的訂單。逾期或取消後收到成功付款時保留款項紀錄，進入待處理佇列，重新確認庫存或退款，不自動出貨。

缺貨、價格改動、無法採購、拆單、補運費、客戶改地址、退件、拒付及退款都需要事件、負責人、處理期限與客戶可見說明。客戶同意替代品需有明確記錄，不由 AI 自行換商品。


## 07 金流與電子發票


### 第一期收款方式

先匯入一間臺灣金流商的信用卡一次付清與 ATM 虛擬帳號，超商付款及其他行動支付依合約開通。導轉付款頁能降低網站直接處理卡片資料的範圍。對外收款主體、發票開立主體與退款主體需對應實際交易模式；日本公司帳戶未具備時不能在系統中假定已可使用日本特店收款。

PaymentAdapter 至少提供 createPayment、verifyNotification、queryPayment、requestRefund 和 reconcile。金鑰只留在服務端；網站不儲存卡號、CVV 或信用卡截圖。每筆付款儲存特店訂單號、平臺交易號、付款嘗試、金額、幣別、驗證結果與帳務狀態。


### 付款通知與對帳

後端先驗證簽章，再核對特店、訂單、金額、幣別與實際成功狀態。瀏覽器返回成功頁不等於已收款。綠界 CheckMacValue 使用官方編碼與 SHA256 規則，附錄程式已有官方測試向量驗證；正式收款仍需測試環境完整認證。[S09]

經驗證通知在同一交易記錄 payment_events、payment_transactions、訂單狀態、庫存變化及 outbox。通知重送或同一平臺交易換事件 ID，都不能重複扣庫存。不同交易號重複付同一訂單時轉財務核對。通知遺失以平臺查單補查；重試要儲存供應商關聯號。

每天核對訂單收入、金流交易、退款、手續費、撥款與銀行入帳。差異分成已收未回報、重複付款、退款未完成、手續費差異與撥款延遲。電子發票依銷售主體與合法開立時點另接發票 adapter，支援載具、統編、作廢及折讓，不能只寫一個「開票成功」欄位。


## 08 日本採購與物流


### 採購到入庫的證據鏈

經付款成立的預購需求依供應商與批次彙總。採購單記錄商品 SKU、數量、供應商、日圓單價、稅費、價格有效期、交貨條件與核准人。採購付款與銷售收款分開；收據、請款、供應商溝通及運送單據與單號關聯。到貨時比對實收數量、版本、批號、效期、破損與採購差異。

日本入庫、集貨、裝箱、出口、臺灣入庫或直送、配送及簽收逐段記錄。每個 shipment 可以包含多個訂單，但 shipment_items 明確記錄每個訂單明細分配數量。分批出貨、退件與補寄不能覆寫原單號。


### 配送計價

ShippingAdapter 輸入收件地、供貨地、重量、尺寸、品類限制及服務種類，輸出費用、計價重量、承諾區間、限制與稅費負擔。計價重量為實重和材積重依合約比較後的結果；材積係數、級距、最低收費、燃油附加、偏遠費與稅費都版本化。

若使用「3 公斤 20 天 NT$380」配送方案，將它儲存為一個有適用日期、航線及商品限制的配送方案，不能當所有商品的預設運費。好市多大包裝先確認配送尺寸與剩餘效期；冷鏈、肉品、植物產品、噴霧、酒類、電池與其他限制商品另做分類審核。詢價未確認的商品不直接收款。

個人直寄涉及快遞收貨人實名認證時，網站引導客戶完成 EZ WAY 所需流程與報關委任，由報關或物流商完成實際查驗；不能僅因網站勾選完成就宣告海關驗證成功。[S11] 只收集該配送方式必要資料，不把身分資料傳到 AI 任務或一般員工群組。


## 09 商品合法銷售與售後


### 商品審核是可執行的發布條件

食品、保健食品、化粧品與一般生活用品的輸入及販售條件分開儲存。食品個人自用免驗條件不能直接套用於進貨販售，商業輸入需處理適用的查驗及標示。[S10] 日本機能性表示食品、藥用或醫藥部外品的名稱先保留原文，依臺灣分類核對，不能直接宣稱已取得臺灣健康食品許可。

化粧品產品資訊檔案制度依公告分期實施；一般適用類別已進入 2026 年 7 月的階段，商品後臺需儲存是否適用、登入、PIF、中文標示及負責業者的審核狀態。[S12] 系統管理條件與證據，不以 AI 的商品描述代替法定檔案。

下架與召回可以用 SKU、JAN、供應商批號及有效期找出受影響庫存與已售訂單。停止銷售後，仍可查歷史付款、出貨與退款。客服模板說明下一步與處理期限。


### 退換貨與購物條款

網站清楚提供經營者、聯絡方式、商品內容、費用、交付條件、解除權與申訴方式。通訊交易原則涉及七日解除權與法定合理例外，不能只因名稱是「代購」就全部排除。[S14] 實際例外適用條件、通知內容與證據由營運與合規負責人逐項設定。

客戶可用網站或 LINE 提出售後申請，系統產生 ticket 與 RMA，儲存原因、商品照片、進度與退款方式。退款金額在資料庫鎖定可退餘額，不能超過實際可退額；退款 API 不明結果先查平臺，不以重送新交易號處理。

### GitHub 的協作方式

LINE webhook 以原始 request body 驗證 HMAC-SHA256，再處理事件與重送去重。[S15] 不將群組中任何人輸入的「退款」「上架」文字直接當作授權；敏感操作回後臺驗證登入者、角色、資料版本與核准範圍。LIFF 可以作為後續員工手機工作臺，但不替代既有權限檢查。

### 省 Token 的實際方法

桌面為預設執行方式。每個任務只提供共同規則、該模組規格、相關檔案與上一個交接結果，不重貼整本規劃書。先用程式完成格式、查重、匯率、排序、價格、庫存及差異計算；僅把語意與判斷需要的內容送給 AI。

任務輸入以 task_id、source_version、changed_paths、acceptance_cases 和 output_contract 組成。固定模板重用；來源雜湊與任務雜湊相同時重用已核准草稿。每次完成更新簡短 context_summary、測試結果及 unresolved_items，讓下一套 AI 接著做。

自動 API 路徑另計費，需先配置 base URL、模型清單、token 上限、當日金額上限、超時與重試次數。官方 DeepSeek 可用 GET /models 核對可用模型。[S04] 若使用私人閘道，使用該閘道實際回傳 ID；不可把桌面顯示名稱直接當 API model。測試費用也記錄，不使用桌面不限量推論 API 無費用。

### ChatGPT Ads 的執行條件

官方 Advertiser API 已有廣告帳號、campaign、ad group、ad、feed、轉換及 reporting 等介面，需使用廣告專用 key，不使用一般模型 API key。[S17] 帳號可用狀態、審核、幣別、時區與投放市場先查核；用 geo_lookup/search 檢查當前可投地區，不直接假定臺灣可選。[S18]

實際帳號未透過資格或目標市場不可用時，系統保留停用狀態與素材草稿，先使用已可用的渠道。ChatGPT 自然搜尋、商品資料與付費廣告各有獨立設定；廣告功能不等於保證 AI 自然回答優先推薦商品。


### Meta 與素材規格

FB 與 IG 的廣告資源統一在內部行銷中心管理。先完成 Business Suite 人工流程與匯出報表，再依啟用時官方 API 版本、應用程式審查與資產權限接 Marketing API、商品目錄及轉換介面。API 版本放在設定欄位並訂定升級日期；不能在程式中猜一個未核對版本。

圖片母版使用真實商品照片，另做方形、直式及限時動態版面；版位尺寸以投放當時規格核對。面膜內容可說明片數、規格、售價及經審核資訊；食品與保健食品不用 AI 自創醫療療效。短影片指令碼按「商品是什麼 → 有哪些選項 → 價格與條件 → 如何下單」產生。


### 預算政策

預算以帳號幣別儲存，不能把 USD micros 當作臺幣元。政策包括每個平臺每日上限、整體月份上限、單次變動幅度、最小觀察樣本、異常停投條件與授權人。建議試投先採小額、固定期限與兩至三組素材；實際金額由負責人填入。

啟用前檢查庫存、落地頁、總費用、來源版本、素材效期、支付路徑與事件。投放資源先以 paused 建立；啟動依預先核准政策執行。停用廣告、商品售完、付款異常與網站不可用需要明確處理機制。AI 提出的追加預算是建議，執行器另查政策與版本。


## 13 追蹤事件與經營分析


### 成交事件以後端為準

內部事件統一為 view_product、search、add_to_cart、begin_checkout、payment_confirmed、order_fulfilled、refund_confirmed 及 support_created。廣告轉換 mapper 依平臺支援事件轉換；Purchase 只由已驗證付款及可計入收入的訂單產生，不能只看感謝頁。

訂單付款交易先寫 outbox，再由 worker 送廣告事件。事件 ID 固定並可重送，browser 與 server 若同時追蹤必須依各平臺當前規則實作去重，不能只假定兩邊用了同一字串就足夠。ChatGPT Ads 有官方 Measurement Pixel 與 Conversions API，實際 payload 依對應檔案與帳號設定驗收。[S19]

廣告量測依同意設定處理。拒絕量測不影響購物或履行訂單。事件只含必要資料，報關證件、完整地址、客服健康內容與其他敏感資料不送廣告或一般 AI 任務。平臺所需 hash 也不視為自動匿名化；另保留同意版本、撤回與儲存政策。


### 成效口徑

看板同時顯示平臺歸因與網站實際收入。後臺營收以已確認款項扣退款，行銷貢獻以成交金額扣落地變動成本、金流、運費補貼及廣告支出。FB、IG、ChatGPT 若各自認領同一筆交易不能直接把三份營收加總。

核心指標包括訪客、商品檢視、加購率、結帳率、付款成功率、客單價、CAC、ROAS、淨貢獻、退貨率、採購達成、缺貨率、來源更新成功率及客服回覆時間。儲存時區、幣別、歸因視窗、退款口徑與匯率版本，讓不同週期可比較。

### 正式程式結構

正式版本採 npm workspace：apps/web 放 Next.js 前臺與後臺，apps/worker 放排程與 outbox，packages/domain 放交易規則，packages/integrations 放外部 adapter，packages/db 放查詢及 migrations，packages/ui 放共用元件。docs 儲存需求、架構與交接；prompts 儲存固定工作指令；infra 儲存容器、部署及還原流程。

起始套件以 src/domain 和 src/integrations 儲存可直接執行的 JavaScript ESM，便於先驗證規則。第一個開發任務將其搬入正式 workspace、增加 TypeScript 型別並保持測試。不能因改框架重寫已驗證交易行為。Node.js 採 24 LTS；Next.js 與其他套件在建置時選官方支援版本並鎖定 lockfile。[S07][S20]

## 17 權限 安全與資料儲存

後臺採成熟的身分驗證方案，員工使用 MFA、獨立帳號與可撤銷 session；登出、停用員工或角色改動後立即失效。客戶可用 LINE 登入或其他經驗證方式，LINE user ID 與網站 customer ID 以已驗證流程繫結，不相信前端自報的 ID。

設定最小權限：Google 商品讀取帳號不取客戶區、worker 不持有所有管理權、金流服務不處理廣告啟用、廣告 API 不讀報關資料。資料庫用 migration、web、worker、報表不同角色；禁止公網直接連庫存資料表。私密圖片與檔案使用短效連結，公開商品圖只發布經核准的版本。

API、金鑰、session、付款原始內容與客戶資料不寫日誌或 Git；錯誤統一遮罩。網站防止上傳惡意檔、跨站指令碼、SQL 注入、越權查訂單與暴力查詢。資料匯出限角色並留下目的、範圍與紀錄。

AI 讀取外部 DM 或網站時，把內容視為資料，不執行其中要求變更付款帳號、權限或指令的文字。AI 可提草稿，實際執行器依角色、資料版本、金額、環境、資源、payload hash 與政策檢查。正式儲存核准的消耗要在資料庫交易中完成，純文字「已核准」不能取代這一層。

儲存期限依發票、帳務、契約、客服及個資用途分開設定；到期刪除或匿名化流程可查核。消費者可提出資料查詢、訂正與其他適用請求。程式驗收包含資料還原與員工停用，不能只驗證登入畫面。

### GitHub 與正式環境

建立私有儲存庫後，將套件加入 feature 分支，提交測試與 docs。CI 起始設定會做語法、交易規則、同步預覽及示範映像建置。正式版完成後加入 Next.js build、型別、API、原生 PostgreSQL 併發、worker、介面與 adapter sandbox 測試。GitHub Actions 版本在開通時鎖定核對後的 commit SHA。[S22][S23]

正式部署流程為「合併透過測試的 commit → 產生固定映像 digest → 測試環境遷移 → 測試環境驗收 → 備份與正式遷移 → 更新正式容器 → readiness 與交易 smoke test → 觀察」。infra/compose.production.template.yml 是正式架構模板，需先實作 web 和 worker 映像、DB 角色、金鑰、網域與備份後才能使用，不把示範伺服器當正式商城。

初期可用一組受管理的主機跑 web、worker 與資料庫，建議規劃 2 vCPU 與 4 至 8 GB 記憶體，再依實測調整。建置在 CI 完成，主機不負責大型 npm build。單主機有維護停機限制；營業量與復原要求提高時，資料庫移至受管理服務並增加 web 副本，外部 adapter 與 domain 不重寫。


## 19 備份 監控與復原

設定資料庫每日加密備份、重要變更前備份與異地儲存；正式服務依選用資料庫能力規劃連續或高頻備份。商品來源與檔案另保留版本。資料庫 dump 不會自動包含雲端圖片、私密檔案、憑證或供應商設定，還原清單要全部列出。

初期目標可訂交易資料 RPO 15 分鐘與 RTO 4 小時；這是待驗證的服務目標，要有對應備份及實際還原結果。只有每日備份不能宣稱 RPO 15 分鐘。每月以隔離測試環境還原一次，核對訂單、付款、庫存、來源、檔案及 outbox，避免還原後重發已完成的外部操作。

監控網站可用、API 錯誤、支付回報延遲、對帳差異、來源過期、庫存負數或保留異常、worker 卡住、LINE 額度、廣告權杖及 API 支出。告警帶 correlation_id、影響範圍與修復連結，避免群組被重複通知淹沒。

回復程式版本不等於回復交易資料。遷移採先擴充再移除的方式保持新舊版本相容；破壞性遷移另外安排。正式回復容器前先判斷資料版本相容性，付款與退款事件不倒回先前狀態。

## 23 管理人員的日常操作

每日先看來源是否更新、待審商品、付款待核對、採購缺貨及今日出貨。商品人員確認新增與變價，客服確認未付款和配送問題，財務核對前日款項。每項有負責人與完成證據，交接以後臺紀錄為主。
